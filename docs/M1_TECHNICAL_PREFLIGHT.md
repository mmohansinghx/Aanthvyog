## 2. Node.js compatibility and safe update proposal

Catalyst's current security floor is Node.js `24.22.1+` or `22.23.4+`. Node.js `24.22.3` is the latest Node 24 LTS release published on 2026-11-11 and meets that floor. The local `24.13.1` is behind it. The official Node 24 archive associates npm `11.19.1` with the current v24.22.3 distribution. Next.js's documented minimum is Node `20.9`, so Node 24 satisfies the framework minimum.

**Proposal at preflight (later authorized and completed):** download the official Node.js v24.22.3 Windows x64 ZIP, verify its signed SHASUMS, extract it into a versioned user-writable directory, and prepend that directory only to a temporary PowerShell process PATH. This allows a side-by-side compatibility trial without replacing the installed Node or editing machine-wide PATH. Verify the resolved runtime with `node --version`, `npm --version`, and `Get-Command node,npm`; keep the system installation/PATH untouched.

**Compatibility risk:** Catalyst Slate currently offers Node 22 for framework applications; its Next.js runtime executes Node while serving requests. Catalyst Functions documents Node 22 and 24. Use Node 24.22.3 locally for the CLI/Functions target, then test Next.js under Slate's supported patched Node 22 runtime (`22.23.5` is the current Node 22 LTS patch) before choosing the hosted runtime. Existing `firebase-tools` and pnpm should be rechecked in the isolated Node 24 shell. Do not update Node or install a version manager during this preflight.

Sources: [Node 24.22.3 release](https://nodejs.org/en/blog/release/v24.22.3), [Node 24 release archive](https://nodejs.org/en/download/archive/v24), [Catalyst Node security notice](https://docs.catalyst.zoho.com/en/announcements/2026/node-security-update/), [Next.js system requirements](https://nextjs.org/docs/app/getting-started/installation), [Catalyst Slate runtime settings](https://docs.catalyst.zoho.com/en/slate/help/monitor-deployment/).

## 3. Catalyst CLI installation plan

The official Catalyst CLI release notes list `1.27.2` as the latest stable release on this review date. The official pinned install command is:

```powershell
npm install -g zcatalyst-cli@1.27.2
```

Catalyst's Windows install guide says the global install should run from an Administrator terminal. The current npm global prefix is user-scoped, but permissions have not been tested; do not elevate or install until separately approved. A global npm install makes the `catalyst` executable available on PATH for the selected npm/Node environment and can alter that environment's global tool set. If using a different Node version or user prefix, CLI visibility may differ. Prefer the isolated Node 24.22.3 environment; inspect the active `npm config get prefix` before an approved install and avoid a machine-wide change where possible.

After installation (not now), verify:

```powershell
npm --version
catalyst --version
Get-Command catalyst
```

Expected CLI version: `1.27.2` unless official release notes have advanced by the installation date. Do not run `catalyst login`, `catalyst init`, `catalyst deploy`, or any project-creation command in this phase. Catalyst configuration must later be generated by the official CLI, never hand-authored.

## 4. Frontend implementation architecture

**Proposal at preflight; local scaffold later authorized and implemented:** Next.js App Router, TypeScript strict mode, Tailwind CSS, and npm. Next's default scaffold supports TypeScript, Tailwind, ESLint, and App Router. See the dependency and implementation evidence in [Technology Registry](TECHNOLOGY_REGISTRY.md).

Proposed routes:

- `/` public AANTVYOG landing page.
- `/login` invite-only Catalyst hosted-auth entry; no public registration UI.
- `/dashboard` authenticated, owner-scoped project list.
- `/projects/new` structured project/request creation.
- `/projects/[projectId]` project details, requirements and lifecycle.
- `/projects/[projectId]/approval` exact spec-version review and approval.
- `/projects/[projectId]/activity` persisted lifecycle/audit activity.

Proposed shared components: `Button`, `TextField`, `TextArea`, `Select`, `FormField`, `Card`, `StatusBadge`, `Breadcrumb`, `Dialog`, `Skeleton`, `EmptyState`, `ErrorPanel`, and `RetryAction`. Use semantic elements and typed props; keep route data access separate from domain and validation code.

Proposed visual system: mobile-first, calm, low-noise workspace; semantic CSS tokens for brand, surface, text, border, focus, and status colors; consistent spacing/type/radius scales; no external font or tracking service in M1. Exact brand colors require founder confirmation. Target 360 px mobile, 768 px tablet, and 1280 px desktop layouts. Propose WCAG 2.2 AA as the accessibility target, subject to founder confirmation: keyboard access, visible focus, labelled fields, screen-reader status announcements, reduced motion, sufficient contrast, and status cues that do not rely on color alone.

Every screen needs explicit loading, empty, validation, unauthorized/not-found, network/server error, retry, and stale-data states. Demo fixtures must be clearly marked and run through a separate fixture adapter. Never display simulated agent completion or successful AI execution.

## 6. Versioned data model and API contracts

**Contract version:** HTTP `/api/v1`; JSON `schemaVersion: 1`. This is a proposal only. Database tables and API endpoints have not been created.

### Entity contracts

| Record | Version 1 fields | Rules |
|---|---|---|
| `IdentityRefV1` | `schemaVersion`, `id`, `provider`, `providerSubject`, `createdAt`, `status` | Opaque identity reference only; unique `(provider, providerSubject)`; no password/token storage. |
| `ProjectV1` | `schemaVersion`, `id`, `ownerUserId`, `name`, `category`, `status`, `createdAt`, `updatedAt`, `rowVersion` | Exactly one owner; `ownerUserId` assigned by server, not accepted from write body. |
| `ProjectRequestV1` | `schemaVersion`, `id`, `projectId`, `ownerUserId`, `requestVersion`, `goal`, `requirements`, `state`, `createdAt`, `updatedAt`, `idempotencyKey`, `rowVersion` | Owner must match project; requirements use an allowlisted, bounded structure. |
| `TaskLifecycleV1` | `schemaVersion`, `id`, `projectRequestId`, `projectId`, `ownerUserId`, `state`, `updatedAt`, `rowVersion` | Tracks request lifecycle only; no agent execution or generated-code state in M1. |
| `SpecificationVersionV1` | `schemaVersion`, `id`, `projectRequestId`, `version`, `content`, `contentSha256`, `createdAt`, `createdBy` | Immutable version; changing content creates a new version/hash. |
| `ApprovalV1` | `schemaVersion`, `id`, `projectRequestId`, `specificationVersionId`, `specificationHash`, `decision`, `actorUserId`, `decidedAt` | Server binds decision to current persisted spec hash and authenticated actor. |
| `AuditEventV1` | `schemaVersion`, `id`, `ownerUserId`, `projectId`, `requestId`, `actorType`, `actorId`, `action`, `targetType`, `targetId`, `occurredAt`, `correlationId`, `previousEventHash`, `eventHash`, `safeMetadata` | Append through API only; deterministic hash chain detects record alteration, but the database is not claimed to provide immutable/tamper-proof storage. |

Proposed requirements object: `targetUsers[]`, `requiredPages[]`, `features[]`, and `constraints[]`. Initial validation candidates: project name 1–80 characters; goal 1–2,000; at most 10 target-user entries, 20 pages, and 40 feature/constraint entries; each list value at most 240 characters. These caps are implementation proposals, not approved product limits. Reject unknown write fields and over-limit payloads. Server controls identity, owner, IDs, timestamps, states, row versions, and hashes.

### Ownership and authorization

For every protected operation: verify the Catalyst identity on the server; derive the caller ID from trusted identity claims; load the target record and parent project; require `callerId == Project.ownerUserId` and child `ownerUserId == Project.ownerUserId`; then validate action and state. IDs alone never grant access. Keep workspaces/memberships out of M1. Data Store scopes/permissions are defense in depth. Return a non-disclosing not-found/forbidden response for another user's resources.

### Lifecycle state machine

```text
draft -> submitted -> needs_information -> submitted
                   -> specification_ready -> awaiting_approval
                                            -> approved -> cancelled (before any future execution)
                                            -> rejected
Any nonterminal request -> cancelled
failed is allowed only for an actual recorded system operation failure.
```

M1 does not create `agent_running`, `agent_completed`, or `generated_code_ready` states. Every allowed transition is a server-side command with optimistic `rowVersion`, actor/time, and a matching audit event. Approval is rejected if the submitted version/hash is stale. Cancellation blocks later work and records actor, time, and reason.

### API surface proposal

| Method | `/api/v1` resource | Purpose |
|---|---|---|
| POST / GET | `/projects` | Create project (server sets owner) / list only caller-owned projects. |
| GET / PATCH | `/projects/{projectId}` | Read/update owner-validated project metadata. |
| POST / GET / PATCH | `/projects/{projectId}/requests` and `.../{requestId}` | Create/read structured request; update requirements through validated transitions. |
| POST | `/projects/{projectId}/requests/{requestId}/approval` | Record approve/reject against exact specification version/hash. |
| POST | `/projects/{projectId}/requests/{requestId}/cancel` | Cancel a nonterminal request safely. |
| GET | `/projects/{projectId}/requests/{requestId}/activity` | Read owner-scoped persisted lifecycle and audit events. |
| GET | `/me/export` | Export only the authenticated user's owned records in the documented v1 format. |
| POST | `/me/deletion-requests` | Begin a confirmed deletion workflow; retention exceptions and audit treatment must follow the approved policy. |

Proposed safe error envelope:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "The request could not be accepted.",
    "correlationId": "server-generated-id",
    "details": []
  }
}
```

`details` may contain sanitized field names/rule codes only. Never return another user's record, raw stack trace, secret, or provider error.

## 7. Realistic test plan

Proposed tools: Vitest for domain/schema/state-machine unit tests; Playwright for browser flows, access control, and Next.js async Server Component behavior. Integration tests use isolated Catalyst development data only after account/region/billing approval. A test is **not passed** until executed and recorded. No test was run for this preflight.

- **Authentication/invites:** unauthenticated calls denied; public signup absent; admin invite and password setup work; recovery and expired/revoked invite links follow documented behavior; development account user cap respected.
- **Ownership:** create two users and projects; exercise every GET/PATCH/approval/activity/cancel endpoint with the wrong owner, spoofed owner field, guessed IDs, and child/parent mismatch; all must fail without object disclosure.
- **Input validation:** invalid enum, missing/unknown fields, oversized request/array, malformed ID, stale rowVersion, duplicate idempotency key, and malicious text are rejected safely.
- **Lifecycle/approval:** table-driven tests cover every permitted/forbidden transition; approval stores actor/version/hash; stale or changed spec hash cannot be approved; cancellation blocks subsequent work.
- **Audit integrity:** each transition has exactly one matching append event; normal APIs cannot update/delete prior events; verify sequence/hash mismatch detection and ensure audit metadata contains no tokens/secrets. Do not claim protection from a privileged database administrator.
- **Safe errors:** auth, validation, conflict, missing resource, data-store outage, and unexpected error shapes are stable and contain correlation IDs only; no stack/secret/cross-owner data leaks.
- **Export/deletion:** export is owner-scoped and includes documented user data; deletion follows approved retention/audit policy; verify provider backup behavior separately and make no unsupported deletion claim.
- **Responsive/accessibility:** keyboard-only operation, labels/focus/status announcements, contrast, reduced motion, and route layouts at mobile/tablet/desktop sizes.
- **Demo separation:** fixture mode is visibly identified; fixture adapter cannot masquerade as a persisted API response or completed agent task.

## 8. Zero-spend controls and risks

Current state: no Catalyst project or remote activity. Keep remote integrations disabled, AI/provider calls at zero, Slate deployment at zero, and production deployment disabled.

The current Catalyst free-tier page lists, among other allowances, 25,000 Functions GB-seconds, Data Store 10,000 SELECT / 5,000 INSERT / 1,000 UPDATE / 1,000 DELETE operations, Slate 12 GB-minutes of build/deploy and 25,000 GB-seconds of invocations, and DevOps 100 automated test cases. The vendor says these figures assume a single component uses the whole allowance; limits vary when components are combined. The account-wide allowance is shared across projects. Public Catalyst docs warn that over-limit usage can be billed and a USD 5 minimum can apply per project with billable activity. Development usage is not automatically isolated from billing.

**Proposed post-approval guardrails (not implemented or account-verified):**

1. Default `REMOTE_CATALYST_ENABLED=false`, `AI_ENABLED=false`, `DEPLOY_ENABLED=false`; require an explicit operator action to enable development services.
2. Before first remote operation, inspect account-wide billing mode, usage, and alerts. If status/quota is unavailable or other-project consumption is unknown, keep remote access paused.
3. Allocate AANTVYOG no more than 10% of the current remaining monthly free allowance for each metered resource; hard-pause at 80% of that allocation or 70% of the account-wide allowance, whichever occurs first. This leaves a reserve and must be recalculated from the live account meter; published quota numbers alone are not sufficient.
4. Bound retries to one idempotent retry; no background polling/agent loops; require manual task submission; cap invite-only development accounts at five named testers; send no unnecessary emails.
5. Keep Slate builds/deploys at zero until a separate review confirms the free-tier meter and founder approves a dev preview. Never configure auto-deploy. Use local Next/Functions development for routine work.
6. Application-level pause control blocks writes/dispatches; an operator kill switch disables all remote Catalyst calls. Review account usage daily during any approved development test and stop before the threshold.

Potential metered services: Functions compute, Data Store storage and reads/writes, Authentication/invitation email, Slate build/runtime/requests, Catalyst DevOps test/pipeline activity, and any future logging/storage integrations. Avoid AI/ML services in M1. An internal throttle alone cannot guarantee INR 0 if the shared account allowance is already consumed or the vendor usage meter/billing state is unclear.

Sources: [Catalyst free-tier usage](https://catalyst.zoho.com/free-tier/), [Catalyst free-tier/billing FAQ](https://docs.catalyst.zoho.com/en/faq/general/), [Catalyst pay-as-you-go minimum billing](https://docs.catalyst.zoho.com/en/deployment-and-billing/billing/pay-as-you-go-model/).
