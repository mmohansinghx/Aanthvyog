# Phase 2A — Database Design

**Status:** In Design — logical schema proposal v2, 2026-11-12
**Implementation/test status:** No database, tables, migrations, or persisted application records exist.
**Provider status:** Catalyst Data Store is proposed. This schema is not approved for deployment and must be verified against the selected India account and service behavior.

## Design principles

- One internal application user owns each project in M1. Collaboration/workspaces are deferred; migration must preserve owner and event history.
- Every project-scoped table contains owner_user_id, project_id, and parent identifiers as applicable. The server derives owner_user_id from a verified identity, never from request JSON.
- Every read/write verifies the project's owner and confirms the child row belongs to that project and owner. Query filtering or Catalyst table scopes alone are insufficient.
- Store only the provider name and opaque subject needed for identity mapping. Do not store passwords, session/access tokens, invitation URLs, payment data, or unnecessary personal data.
- API-visible IDs are random UUIDs in public_id fields; Catalyst ROWID remains an internal database key and is not treated as an authorization secret.
- All schemas and serialized JSON have explicit versions and size limits. Rows are append-only where they record decisions/audit; immutable behavior is enforced by service design and verification, not assumed from the provider.
- Export and deletion are user-rights operations subject to an approved retention policy. Backup deletion behavior is unverified; never promise immediate removal from provider backups.

All child relationships also carry owner_user_id. Before each operation, server code must load/verify the parent project and check child.owner_user_id == project.owner_user_id == authenticated app user. Foreign-key integrity does not authorize access.

## Catalyst Data Store mapping and known limits

The public Data Store documentation describes a relational table store. Each table receives platform-managed ROWID (BigInt primary key), CREATORID, CREATEDTIME, and MODIFIEDTIME columns. These do not replace owner_user_id; CREATORID is a Catalyst account-user identity, not necessarily the app end-user.

Documented column types include Text (max 10,000 characters), Var Char (max 255), Date, DateTime, Int, Double, Boolean, BigInt, Foreign Key, and Encrypted Text. Foreign-key deletion choices are Null or Cascade. The documented default is up to 100 columns per table. ZCQL documentation/FAQ describes at most 300 rows per query operation and up to four joins in one query. Data Store Search indexes are documented for Catalyst Search; they must not be assumed equivalent to arbitrary composite query indexes. Confirm query-index semantics, column constraints and practical limits in the actual account.

**Transaction/concurrency blocker:** the reviewed documentation describes Data Store as an OLTP, transaction-oriented CRUD store, but does not establish the specific multi-row atomic commit/rollback, conditional compare-and-set, isolation, uniqueness-race, or audit/domain-write guarantees this lifecycle needs. Treat all of those as UNVERIFIED. Do not implement approval or state transitions as if atomicity exists until an approved, reproducible account test proves the required operations. If it cannot be proven, stop and re-evaluate the provider/design with the founder.

## Key and common-field conventions

| Name | Type | Rule |
|---|---|---|
| ROWID | Platform BigInt PK | Internal only; generated by Catalyst. |
| public_id | Var Char(36), unique | Server-generated UUIDv4/UUIDv7-compatible opaque identifier; API exposes this, never ROWID. Exact UUID policy to be selected before implementation. |
| owner_user_id | Foreign Key -> APP_USERS.ROWID | Required on every project-scoped record; set from verified server identity. |
| project_id | Foreign Key -> PROJECTS.ROWID | Required on all project-scoped child records. |
| schema_version | Int | Positive current serialized contract version; unknown versions rejected. |
| row_version | Int | Starts at 1, incremented on each mutable aggregate update. Conditional update support must be verified before relying on it. |
| created_at / updated_at | DateTime | App-owned UTC instant. Catalyst CREATEDTIME/MODIFIEDTIME are also retained for provider diagnostics but are not a substitute for domain timestamps until timezone/precision are verified. |
| idempotency_digest | Var Char(64), unique | SHA-256 over authenticated owner ID, HTTP method, canonical route, and Idempotency-Key. Never store the raw client key. Unique-column behavior is documented; atomic insert/replay behavior must be tested. |

Catalyst's unique constraint is described at the individual-column level. Do not assume composite unique constraints are supported. Where multi-column uniqueness is required, use a deterministic digest field with a single-column unique constraint only after verifying its creation and concurrent behavior. If that cannot be verified, gate the write path.

## Proposed entities and fields

Types below use the Catalyst names above. “Required” means non-null in the logical contract; actual provider enforcement must be checked. Omitted common fields are ROWID, CREATEDTIME, and MODIFIEDTIME. No table is created in Phase 2A.

## Relationships, referential rules, and indexes

- APP_USERS 1:N PROJECTS; project_requests, specs, tasks, dependencies, approvals, audits, artifacts, and user usage rows all repeat owner_user_id.
- PROJECTS 1:N PROJECT_REQUESTS, AUDIT_EVENTS, ARTIFACTS, and USAGE_RECORDS.
- PROJECT_REQUESTS 1:N SPECIFICATION_VERSIONS and TASKS.
- TASKS 1:N TASK_DEPENDENCIES and TASK_ATTEMPTS; dependencies point to two tasks in the same project.
- SPECIFICATION_VERSIONS 1:N APPROVAL_RECORDS.
- Foreign-key deletion behavior must not physically cascade audit/approval history. Prefer logical deletion and policy-driven child redaction/deletion. Confirm FK action and write ordering in the account before use.
- Required filters: owner_user_id plus project_id and parent ID for all user-scoped queries. Add indexes for these predicates and sort keys only after verifying Catalyst index behavior.
- Pagination uses bounded pages no larger than 100 rows, stable sort keys, and opaque owner-bound cursors. Do not depend on undocumented offset behavior or retrieve all rows in one query.
- Report-level uniqueness constraints: public_id; APP_USERS.identity_key; request idempotency digest; spec version key digest; task idempotency/attempt key digests; approval idempotency digest; audit event digest; dependency relation digest; system config scope digest. Verify each field's unique constraint and concurrent insert semantics.

No retention duration is approved for any entity; each row below is a policy requirement, not a deletion guarantee. Exact durations, legal exceptions, and backup behavior must be approved before implementation/release.

|---|---|

## Input, lifecycle, and persistence validation

- Request payload max 16 KiB; strict JSON object, maximum nesting depth 8; unknown mutation fields rejected.
- Project name: 1–120 UTF-8 bytes after trim. Category: allowlist. Goal: 1–4,000 UTF-8 bytes.
- Structured requirement arrays: each max 25 entries; each entry max 300 UTF-8 bytes; bounded arrays for target users/pages/features/constraints; total canonical request JSON max 8 KiB.
- Specification canonical JSON max 8 KiB. Reject oversized input with a stable error; do not truncate silently or move content into Stratus without approval.
- IDs must match the expected opaque public ID shape; owner, timestamps, state, actor, version, and hash are server-controlled.
- Hash content using a pinned, tested canonical JSON algorithm and SHA-256; recompute server-side from persisted content on approval.
- For every write: authenticate; resolve user; validate body; load project; verify owner; load child; verify project and owner; validate lifecycle and expected row/spec version; apply idempotency; persist domain change and audit event; return result only if required records are consistent.
- If atomic transaction/CAS is not available, the last step cannot safely be asserted. Stop the operation or obtain an approved alternative consistency strategy; do not return success with a partial approval/state/audit record.

## Retention, export, deletion, and recovery

No duration is approved yet. Before implementation/release, set retention per identity reference, request, spec, task/attempt, approval, audit, artifact and usage class; define account closure; define what is erased versus minimally retained for fraud/security/accounting; and have qualified counsel review applicable privacy obligations.

Export must include only the authenticated user's owned data, a documented schema/version and UTC timestamps, and no provider secrets or other user's data. Test it against a second user's records. Deletion must re-authenticate/confirm the user, stop future work, mark account/projects pending, perform ordered deletion or de-identification, record permitted audit evidence, and show completion/partial status safely. Provider backup expiry/deletion timelines remain UNVERIFIED; retain no claim until written provider confirmation. Backup and restore must be tested before production; this design does not imply Catalyst backups are enabled or sufficient.

## Provider-fit decision and verification checklist

Catalyst Data Store can represent the proposed normalized records using documented column types and foreign keys. Its documented 100-column/table default is sufficient for these narrow tables; the 10,000-character Text cap requires content limits. However, fit is **conditional**, not approved: verify unique field constraints, owner-filter query patterns, composite/index/sort/pagination behavior, FK timing/delete behavior, API/SDK parameterization, transaction/rollback, conditional update/CAS and isolation, concurrent insert behavior, request/function limits, export and deletion behavior, backups, and regional availability. Test failures or undocumented critical guarantees block adoption. No alternative provider is selected; any change needs a reviewed ADR and founder approval if it changes cost/data location.
