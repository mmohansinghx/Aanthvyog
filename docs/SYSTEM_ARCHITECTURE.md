# System architecture

**Status:** In Design
**Architecture state:** the local-only frontend preview is implemented; no connected backend, authentication, persistence, or Catalyst project is implemented.

## Decision status

- **Founder Approved (2026-11-12):** India is the intended data region; authentication must be real and invite-only; core platform records must use real persistence.
- **Founder-authorized local frontend:** Next.js App Router, TypeScript, Tailwind CSS. Local preview source is under `apps/web` and uses static demo fixtures.
- **Proposed connected-service baseline:** Catalyst Slate evaluation for frontend hosting, Catalyst Functions with Node.js, Catalyst Data Store, and Catalyst Authentication.
- **Proposed constraint:** Functions-first. AppSail is excluded from M1 unless a documented technical requirement shows Functions cannot meet it.
- **Not approved/configured:** actual account region selection, Catalyst project initialization, paid usage, production deployment, model provider, AI calls, and generated-code execution.
- **Evidence state:** the founder approvals do not mean technically verified, implemented, or tested. See [Decision Register](DECISION_REGISTER.md).

## M1 product boundary

M1 is a secure project and request lifecycle. Local preview screens now include a landing page, dashboard, browser-only structured request preview, project details, sample status tracking, disabled approval actions, activity examples, and access-status explanation. These screens are not authenticated or connected to data. Agent activity is explicitly empty/not connected; no AI calls or generated-code execution exist.

## Proposed logical components

1. **Web frontend:** a local Next.js App Router/TypeScript/Tailwind preview exists. It renders static fixtures; the request form holds temporary state in the browser and sends no request. Future browser code must not hold secrets or decide access rights.
2. **Backend API:** Catalyst Functions (Node.js) validate input, verify authenticated identity, enforce ownership and state transitions, call persistence, and return safe structured errors.
3. **Identity:** Catalyst Authentication is the proposed provider. Public signup stays disabled. An administrator-controlled invitation process is required. Password recovery is expected to use supported Catalyst flows, subject to verification in the actual account.
4. **Data layer:** Catalyst Data Store is the proposed persistent store for identity references, projects, structured requests, task lifecycle, approvals, and audit events. No table/schema exists yet.
5. **Frontend deployment:** evaluate Catalyst Slate compatibility for the selected Next.js app and India data center. This is not a production deployment decision.
6. **Audit/usage controls:** append lifecycle and security events; apply internal usage ceilings and pause controls before any unapproved chargeable operation.

## Application structure

The local frontend structure exists. Backend/auth/data adapters and Catalyst Functions are not created.

## Explicit M1 exclusions

No AppSail unless Functions are shown to be insufficient; no AI model/provider configuration or API calls; no generated-code execution; no unrestricted public registration; no payment method, paid subscription, paid API, chargeable overage, or production deployment. Target operating cost is INR 0. Clearly marked UI demo fixtures must be distinct from records returned by the real persistence layer.

## Identity, ownership, and authorization

- Use an individual-account model for M1, with exactly one `owner_user_id` per project. Do not introduce workspaces or collaboration until a later approved migration.
- Derive the user identity from a server-verified Catalyst session/token. Never accept `owner_user_id` from the browser as authority; set it on the server at record creation.
- Every protected project, request, task, approval, and artifact operation must check the project's owner on the server. A record ID alone is not authorization.
- Keep Catalyst roles and table permissions as defense in depth, not a replacement for application-level ownership predicates. Verify whether chosen server credentials bypass end-user scopes before implementation.
- Future workspace migration must preserve the original owner and audit history; see [Migration Guide](MIGRATION_GUIDE.md).

## Request lifecycle proposal

Persisted transitions are server-validated and audited. Proposed states: `draft`, `submitted`, `needs_information`, `specification_ready`, `awaiting_approval`, `approved`, `rejected`, `cancelled`, and `failed`. Allowed transitions, concurrency behavior, retry semantics, and terminal-state rules are detailed in [API Documentation](API_DOCUMENTATION.md). An approval is tied to an immutable specification version/hash. M1 stops at recording approval; it must not dispatch an agent or imply execution.

## Data and privacy

Store only a provider identity reference and minimum profile data needed for account operations. Do not collect sensitive personal information that is not necessary for the product. Provide an export and deletion path for owned project data; define retention periods and audit-event handling before production. Ask Catalyst for a written, component-level statement about processing, storage, and backups. Do not promise a backup deletion schedule unless the provider confirms it.

## Proposed flow

Invite -> authenticate -> create owner-bound project -> enter structured request -> validate and persist -> review specification version -> approve/reject/cancel -> show persisted status and audit history. M1 contains no model-call or generated-code stage.

## Trust boundaries

- **Browser to API:** untrusted input; authenticate, validate, authorize, rate-limit, and return redacted errors server-side.
- **Function to Data Store:** trusted service boundary; use least privilege and an explicit `owner_user_id` predicate on all user-scoped reads/writes.
- **Admin invitation:** restrict console/API invitation ability to named administrators; audit invite, revoke/disable, and recovery actions where the provider exposes events.
- **Usage/billing:** account-level quotas may be shared across projects; application ceilings must pause work before limits or billing state become uncertain.

## Deployment and local development

No remote Catalyst project is authorized for creation yet. A checksum-verified Node.js 24.22.3 binary is available side-by-side for local work; the system Node installation and machine-wide PATH were not changed. Before Catalyst initialization: confirm the actual Zoho account data center is India; check component support; review the data-residency statement, billing state, free-tier allowances, and invite configuration; verify CLI/runtime compatibility; then obtain explicit founder permission for global CLI installation, login, and project initialization. Use the official CLI to generate Catalyst files; do not hand-create Catalyst configuration. Keep local secrets out of Git; keep preview fixtures separate from real data.

## Reliability and API behavior

Persist a state transition and corresponding audit event atomically where the chosen store allows; otherwise use an idempotent write/reconciliation design. Use idempotency keys and version checks for retries/concurrent updates. Bound request size, pagination, execution time, retries, and usage. Cancellation prevents later lifecycle work from starting and records actor/time/reason. Return a stable error code, safe message, correlation ID, and only sanitized field-level details.

Local Node and frontend build are verified, but no Catalyst or account-level check is complete.
